# AxiaPay Android architecture

The app preserves its illustrative payment preview while dev/staging/prod integrate account access, owned wallet display and immediate single airtime and data purchases with the authoritative API. Other billers/banks, background execution, real SMS transport and push notifications remain outside the mobile integration.

## Boundaries

The project remains one Gradle application module. Named packages provide explicit inward dependencies; `ArchitectureTest` guards those imports. Separate Gradle modules can be introduced when build isolation is useful, without changing these contracts.

- **Domain** contains value models, the repository contract, error types and reusable demo invariants. It imports neither Android nor Compose, JSON, concrete storage, presentation, or provider libraries. `Currency.NGN` is explicit; all monetary values are integer kobo. Outgoing activity is negative and incoming funding is positive.
- **Application** provides one named action or query per use case. `PreparePayment` validates and prepares raw input; `SubmitDemoPayment` revalidates it and asks the repository to atomically apply a domain transition. Other use cases cover completion, bulk validation/queue/run/retry, plan status, visibility, reminders, notification read state, and observation. Sample provider/price choices live in the demo application catalog.
- **Data** owns illustrative fixtures, snapshot serialization and storage coordination. `CheckpointSessionRepository` serializes access to one session aggregate, invokes the supplied transition exactly once, saves before publishing, and leaves the observable snapshot unchanged if storage fails. It does not decide whether a payment is allowed or sufficient funds exist.
- **Presentation** owns immutable MVI state and typed intents. `AxiaViewModel` invokes use cases, handles explicit results, and exposes only a read-only `StateFlow`. `PaymentFormPresenter` is a pure form reducer; business validation is delegated to the application layer. `CheckpointNavigationStore` retains immutable navigation edits and checkpoints them off Main through a small presentation port.
- **UI** renders state and emits intents. It may format values and own framework-only scroll, modal animation and native date-picker state. It cannot mutate the session or invoke a repository. Icons and human-readable labels are presentation details, mapped from domain types at this boundary.
- **Composition root** is Hilt, initialized by `AxiaPayApplication`. `MainActivity` is an `@AndroidEntryPoint` and retrieves its two `@HiltViewModel` owners from the default lifecycle-aware `ViewModelProvider`. Shared modules in `di` provide platform dependencies, presentation collaborators and plain application use cases. Flavor-specific modules select repositories and payment/SMS action implementations. No production hand-written ViewModel factory or service locator remains.

```text
User action → AxiaIntent → AxiaViewModel → application use case
                                             ↓
                                    domain transition/policy
                                             ↓
                                    SessionRepository contract
                                             ↓
                              data: atomic demo snapshot commit
                                             ↓
                           read-only state → lifecycle-aware Compose
```

## Flavor boundaries and backend migration

The single `environment` dimension contains dev, demo, staging and prod, each with a unique application ID. Debug/release remain build types, independent of environment and payment simulation. `BuildConfig.FLAVOR` identifies the selected environment at the composition boundary; it is not a business rule or an authentication mechanism. The resource namespace remains stable.

- `src/main/` contains the shared UI, domain/application contracts and current sample implementations.
- `src/demo/java/.../di/FlavorPaymentModule.kt` permanently selects demo repository and action bindings.
- `src/nonDemo/java/.../di/FlavorPaymentModule.kt` is added only to dev/staging/prod source sets. It currently selects exactly the same demo wiring; future integrations are selected here.
- Flavor resource overlays distinguish launcher labels without changing in-app screens.

For each future backend feature, introduce the required application/domain port and its backend adapter, then bind it in the non-demo composition path. Preserve the existing simulated implementation and bind it in the demo path. Do not silently fall back to sample balances/results on a backend failure. Authentication, payment execution and authoritative financial decisions must move to their backend operations together; replacing a session repository alone is not sufficient. Payment and plan actions now enter through narrow suspending application contracts in `PaymentActions.kt`. The flavor Hilt module binds these to the main-safe suspending local use cases; future backend adapters can suspend without changing the View or intent contract. Preference and connectivity use cases remain concrete local actions. These contracts do not make the demo ledger authoritative.

Backend URLs, credentials, real SMS and release signing remain unconfigured. The non-demo Hilt module is a migration boundary, not a live backend implementation. Keep demo copy and data until each feature's real source is connected; share UI changes so demo remains representative instead of freezing a duplicate UI. The common Android regression suite currently runs against all four flavors; move sample-specific expectations into demo tests as backend behavior arrives, retaining shared behavior coverage.

## State ownership and delivery

The repository owns the session. The ViewModel owns navigation, forms, filters, queries and presentation errors. Its render state includes the repository's immutable session snapshot; Views have no write access. The form's logical request ID is allocated when opening the form and retained through edits, review, and restoration.

Confirmation is accepted only while showing a reviewed payment form. Successful completion replaces that form with a receipt identified by the payment ID only if the user has not navigated or edited the form since submission. The receipt is ordinary render state: recomposition, collection restart and activity recreation never submit an operation. Repository idempotency also handles a process interruption after committing a payment but before saving receipt navigation.

There is no one-shot payment/navigation event channel to replay. Errors are visible state, consumed by an explicit `DismissError` intent or successful navigation. They survive configuration changes in the ViewModel; process restoration restores form/session values and revalidates input, rather than replaying an error or action. The native date picker opens only from its button click and returns a date-selection intent.

Payment/plan/SMS work runs in `viewModelScope`. A main-thread intent entry point sets `isProcessing` before launching, admitting one action at a time. Duplicate taps during suspension cannot launch another operation. Progress is temporary render state and is not persisted. A navigation revision limits result consumption to the originating screen visit; late results still update repository state without replacing newer forms or drafts. Returning to an identical screen is a new visit, not permission to consume an older result.

Cancellation propagates from the action and the storage boundary. It is never converted to payment failure. Unexpected execution exceptions map to `OperationUnconfirmed`, retaining the cause without inventing a final failed payment. Future backend implementations must persist and reconcile uncertain outcomes under the same logical ID; ViewModel lifetime is not a durable execution queue. Application contracts require main-safe work: adapters move blocking I/O to injected dispatchers, while SavedStateHandle access remains on Main and stores only small checkpoint metadata. Session mutations serialize on a mutex and an injected worker dispatcher.

`CheckpointSessionRepository` defensively copies and seals payments, plans and SMS lists at load/seed/commit boundaries. Callers cannot mutate a published snapshot by retaining an input list or casting an exposed list to a mutable interface. The repository saves the owned snapshot before emitting it; failed storage cannot publish partial changes. No stability annotation is used to pretend arbitrary Kotlin collections are immutable.

The Activity collects state with `collectAsStateWithLifecycle`. Compose lifecycle changes do not create a new repository while the existing ViewModel is retained.

## Demo payment invariants

- An immediate payment either debits once and records success, or records a waiting request without a debit.
- Adding funds does not automatically execute waiting payments. `CompleteWaitingPayment` is the explicit recovery action and is idempotent for completed requests.
- Balance, receipt and plan changes form one atomic repository transition. Concurrent requests cannot spend the same available funds.
- A reused request ID with changed details returns a conflict. A matching request returns its existing receipt.
- Each bulk batch and recipient has a stable identity. Confirmation reserves the reviewed total once; known failures release their reservation. Explicit retry reserves only failed rows and never repeats successful recipients. Queued/processing rows retain their identity and reservation across interruption, with explicit resume after reconnection.
- Scheduling records a receipt and plan without debiting. Daily/weekly/monthly recurrence is anchored to the original start date; January 31 advances to February's last day and then March 31. Pause/resume changes a plan's enabled value explicitly.
- Storage failures retain their cause in the application result and show a safe UI message. They never turn an unsaved change into success.

These are **local demo simulation rules**, not authoritative financial controls. Real balances, authentication, authorization, pricing, reservations, settlement, server idempotency and reconciliation must be enforced by the backend. No authentication or real provider result is simulated as verified in this build.

## Offline simulation boundaries

`ObserveInternetConnection` reads the domain `InternetConnectionRepository` contract. Its Android adapter observes the app’s default network using `ConnectivityManager`, requiring both internet capability and Android validation. The ViewModel invokes `UpdateConnectionState` for changes, without executing any requests. `PrepareSmsPayment` validates the input and sample airtime/data eligibility, then stores an immutable `SmsRequest` alongside the session. `SendDemoSms` and `ReconcileDemoSms` apply pure `DemoSmsPolicy` transitions through the same repository; there is no real transport adapter yet. Only the composition root knows concrete storage implementations.

Transport (`Draft`, `SendFailed`, `Sent`) is separate from the payment ledger. A sent request with no ledger result remains uncertain. Sending, reopening the sheet, recreation and reconnecting cannot debit the wallet. Explicit simulated backend confirmation records one payment with the original ID. Matching confirmations replay the result, and ordinary online submission cannot bypass the SMS outbox. Insufficient funds keep the established explicit funding/completion rule.

A draft binds payment terms, SIM and deadline on review. Retries retain these terms and the ID, are limited to three attempts, and cannot start after the 15-minute demo deadline. A sent request can still reconcile after its deadline; expiry must not erase an uncertain outcome. Closing a sheet never cancels a sent request. Sample fees are zero, amounts are exact kobo and carrier SMS costs are outside the payment ceiling.

`NavigationState.draft` retains one unsubmitted form, including partial input, recurrence and SIM selection. It restores and revalidates without running a command. `SessionSnapshotCodec` retains optional offline/cache/outbox fields, so legacy inline snapshots still migrate. Outbox progress is committed before state publication. The storage lifetime is intentionally unchanged: activity/process saved-state restoration, not a production durable queue.

The ViewModel coordinates intents and the UI renders immutable state. The offline palette is a read-only composition local, not business state; all palette tokens resolve per composition so separate bottom-sheet and dialog windows inherit it. Pixel checks cover the home/navigation and SMS sheet. SMS composition/send permissions, encoding, authentication, gateway acknowledgements and backend status lookup remain separate integration work. SMS and backend replies remain explicitly simulated.

## Live connectivity lifecycle

`PlatformModule` provides `AndroidInternetConnectionRepository` using the application’s `ConnectivityManager`; the ViewModel and UI never access Android network APIs. Initial connectivity is read before the first frame. Automatic mode refreshes stale saved connection metadata; an explicit preview override is respected. Both paths leave form/navigation and payment data intact. One ViewModel-scoped flow subscribes to network events and releases its callback when the ViewModel is cleared; activity recreation reuses that owner. No polling, HTTP probes, new dependencies or SMS permissions are needed.

Registration, the initial snapshot, and callbacks are serialized on the main thread. The callback uses supplied capability values, not racy synchronous queries. `onAvailable` alone does not claim internet access. Losing validation or the current default switches offline; a late loss/capability callback for the previous default cannot override a new network. App-blocked networks are also treated as offline on versions delivering that callback. Identical values are coalesced. Monitoring errors retain their cause and show an explicit error with offline fallback in Automatic mode; manual previews keep their selected mode.

The system’s validation is a connectivity signal, not proof that a particular payment backend is reachable. See [Android network-state guidance](https://developer.android.com/develop/connectivity/network-ops/reading-network-state) and [NetworkCallback reference](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback). `ACCESS_NETWORK_STATE` is declared as a normal permission.

## Demo connection override

`ConnectionMode` defaults to Automatic. `SetConnectionMode` reads current real connectivity through the domain port and atomically saves the preference and effective offline state. `UpdateConnectionState` continues receiving real network events while manual mode is active. Both use `DemoConnectionPolicy` to resolve the effective mode and only timestamp entry into offline mode; neither submits, reconciles or changes financial state.

Profile and the connection/outbox panel render the same radio group and emit `AxiaIntent.SetConnectionMode`. A persistent banner labels forced modes as previews and provides a return path to Automatic. The preference is an optional saved-session field (older snapshots default to Automatic); it survives recreation with the existing session lifetime, not permanent storage. Force online enables demo operations without claiming real network access. No real SMS or backend functionality is added.

## Persistence and extension

`CheckpointSessionRepository` and `CheckpointNavigationStore` keep versioned JSON in separate app-private atomic files. SavedStateHandle retains owner IDs and readiness markers; legacy inline snapshots migrate after successful disk checkpointing. JSON objects remain inside adapters. The identity has the same task/session lifetime as the original demo; these bounded snapshots are not durable financial storage or an unbounded history.

For production, introduce backend application ports and repositories for authoritative operations. Keep the Views and intent contracts stable where possible; adapt server responses into domain values. Model unknown provider outcomes explicitly and reconcile by request ID. Introduce a durable database/outbox and workers when offline, scheduled or bulk execution is implemented. Do not put those workflows in a ViewModel or grow the demo repository into a provider service.

## Account access and protected sessions

`AuthViewModel` is the single immutable owner of welcome, account forms, verification, real account confirmation, session restoration and recovery. It calls the `AccountAccess` application operation contract; Views render state and emit typed intents. `DemoAccountAccess` reuses the established preview use cases and simulated adapter. `ServerAccountAccess` coordinates client input feedback, the remote `AuthenticationRepository`, and `AuthenticationSessionStore`. Domain/application code imports no Android, JSON, HTTP or Hilt types. Server authentication and financial authorization remain distinct.

The server workflow implements phone/email signup with/without a password and phone/email sign-in with password/code. It normalizes local Nigerian phone numbers to E.164, preserves email aliases and exact password/code characters, and uses API-compatible Unicode password limits. Every code request returns a fresh, purpose-bound challenge with explicit timing. The password is discarded before verification. Password-signup resend returns to the form for re-entry because the API has no password-preserving resend operation; code-only flows resend without retaining secrets. No authentication error can resolve to demo completion.

`HttpAuthenticationRepository` owns API-specific JSON and HTTP handling. Its application-wide OkHttp pool uses bounded timeouts, supported cancellable `executeAsync`, normal platform TLS, no cache/redirects/retries/logging, and strictly scoped dev cleartext. Responses are bounded and checked before mapping to domain contracts. Safe errors distinguish credentials, rejected/expired code, rate limiting, connectivity, invalid configuration/response and unavailable service without serializing raw response bodies. Request references and `Retry-After` are retained. Redemption is never automatically replayed after a timeout or uncertain response.

`KeystoreAuthenticationSessionStore` owns one encrypted, atomic credential record outside Android backup. The AES-GCM key is non-exportable through Android Keystore and scoped to the app ID; crypto/IO uses an injected dispatcher and local mutex. The record contains only bearer token, expiry and normalized API identity. UI state, SavedStateHandle, logs and payment snapshots never receive bearer tokens. Corrupt ciphertext/key loss requires a fresh sign-in. The application publishes sign-in only after successful persistence; cancellation-resistant network completion is checked before storing credentials. Local expiry/API mismatch clears access without sending the old token to another host.

Startup and appropriate foreground events recheck `/auth/me`. No local token alone proves that the session is still valid. Connectivity failures retain the encrypted record behind a recovery screen; the separate sample payment experience remains explicitly accessible without claiming real authentication. Logout calls the server first and clears the protected record after success; failure is retryable. Cleanup compares the original protected record so a late logout or invalid-session response cannot delete a newer login. Temporary Keystore/IO failures retain ciphertext for explicit retry. There is no speculative token refresh because the API has no refresh endpoint. Password-reset and signed biometric/device flows remain separate scope.

`MainActivity` collects auth and payment state with lifecycle awareness and removes its lifecycle observer on disposal. Foreground checks never replace an unfinished form or replay signup/verification. Dashboard/profile navigation, drafts, pending SMS requests, plans and the greyscale palette retain their independent payment owner. Real account confirmation identifies the verified contact and displays its server wallet separately from the simulated payment preview. The existing profile shortcut returns to account/sign-out actions in server mode; demo keeps its preview shortcut and unchanged simulation.

Only the demo-entry Boolean enters saved state. No contact/name, password, code, challenge, operation or error is serialized. Configuration changes keep the ViewModel. Process restoration of unfinished forms requires new input; protected-session restoration is an explicit independent operation. Navigation cancels work and invalidates late results by screen visit. Owned countdown jobs only update UI and never submit a request. Duplicate taps and local cooldowns are guarded without replacing server validation/rate limits.

Unit checks cover contract mapping, every contact/method, code leading zeros/purpose/expiry, Unicode passwords, cancellation, storage failure, logout, API changes and recovery. Real Keystore/tamper/network-policy device tests are isolated from actual auth records. The opt-in dev flow uses the local API/PostgreSQL/Mailpit through the installed Hilt graph, while existing demo auth and offline tests keep their original semantics. See README for environment configuration and explicit emulator commands.

## Hilt component ownership

- `SingletonComponent`: `PlatformModule` provides the device-zone `Clock` and the application-context connectivity adapter. Sharing the adapter does not add a permanent subscription: its cold Flow still registers/releases one callback per observing ViewModel lifetime.
- `ViewModelComponent`: the compiled flavor's `FlavorPaymentModule` provides the demo session repository and payment/SMS action contracts. `SessionRepository` is `@ViewModelScoped`, so observation, funding, payments, plans and SMS all use one atomic snapshot within that owner; another ViewModel key receives a separate repository.
- `PaymentPresentationModule` provides a `@ViewModelScoped` `NavigationStore` with that component's `SavedStateHandle`, the form presenter and the existing UUID request generator. `PaymentUseCaseModule` constructs plain payment application classes. Demo-only `AuthUseCaseModule` supplies the preserved preview use cases. `FlavorAuthenticationModule` provides an owner-scoped `AccountAccess`: demo selects its simulation; non-demo selects `ServerAccountAccess`. Neither domain nor application imports a DI framework.

Hilt supplies each ViewModel's handle from its owner and key. Small checkpoint identities replace inline session/navigation JSON; codecs remain compatible for migration. Auth and payment owners stay independent. Configuration changes retain the owners, and saved-state restoration reconstructs the same snapshots without replaying commands. Mutable demo sessions must not move to `SingletonComponent` or `ActivityRetainedComponent` without a deliberate ownership and persistence change.

Non-demo `AuthenticationInfrastructureModule` owns the shared application-wide API HTTP transport, auth/wallet repositories and encrypted session store in `SingletonComponent`. This deliberate account/session lifetime does not change the `ViewModelComponent` scope of demo payment snapshots/navigation. Flavor payment bindings still share simulated policies; auth bindings now differ at composition. Dev defaults to the confirmed local API, while staging/prod URLs remain unconfigured until explicitly supplied.

The catalog pins Hilt runtime/compiler/plugin 2.60.1 together and KSP 2.3.12. KSP runs with AGP 9.4.1 built-in Kotlin; no legacy kapt plugin or second Kotlin Android plugin is added. Compilation targets Java 17. The existing Compose compiler version remains unchanged. Compatibility is verified with all flavor debug/release APKs, generated graphs, unit tests and lint, plus installed-graph device flows. `HiltGraphTest` catches accidental unscoped or global session repositories by funding one owner and asserting another owner remains unchanged through auth navigation and Activity recreation.

## Bulk preview ownership

`BulkFormPresenter` reduces immutable quick-list state, parks a separate unfinished draft/editor per service, and delegates same-service/duplicate/amount validation to `PrepareBulkBatch`. Adding a row saves the current valid editor and copies only provider and amount/plan defaults. Review commits the last entered row; a blank new row is omitted, while clearing an existing account remains a validation error. Legacy mixed unsubmitted drafts split into service lists without replaying submitted identities. Single-form expansion retains the form identity as a recipient ID and consumes its single-payment draft alias after transfer. Titles are generated from the service; named groups are deferred. The existing `AxiaViewModel` coordinates explicit queue, retry and run intents, sharing its ViewModel-scoped session repository with single payments. Dedicated Compose screens only render this state and emit intents. No additional ViewModel scope or wallet owner is created.

`QueueDemoBulkBatch`, `RetryDemoBulkBatch` and `RunDemoBulkBatch` coordinate the domain policy through atomic repository transactions. `DemoBulkPolicy` reserves the full reviewed total once, marks recipient attempts, records successful payments once and releases known failures. Retry reserves only failed rows; successful and pending identities remain unchanged. The coroutine advances simulated outcomes in the caller’s scope; it is not durable payment execution. Cancellation preserves uncertain/processing state for an explicit resume. Snapshot codecs restore values without starting commands, while the repository seals nested recipient lists before publishing them. Navigation revisions prevent late results from replacing newer drafts/screens. Flavor modules select the simulations without placing payment rules in DI or presentation.


## Local recipient import

`RecipientImportRepository` is a framework-independent document capability, implemented by `AndroidRecipientImportRepository` using the application content resolver and an injected IO dispatcher. It reads a temporary SAF grant, bounds actual bytes, closes streams/cursors, propagates cancellation and returns typed cells or an explicit failure with its cause. It owns no cache, file persistence, wallet or transaction. Hilt supplies the same stateless adapter in all four flavors; live payment migration does not remove local import or demo fixtures.

`ExportRecipientSample` exposes a separate `RecipientSampleRepository` capability. Demo Hilt bindings select `BundledRecipientSampleRepository`, generating full-size synthetic CSVs or copying service-specific CSV/XLSX assets to a newly created SAF document using an injected IO dispatcher. Non-demo bindings expose no formats and perform no writes; assets live only in `src/demo/assets`. The import ViewModel owns explicit picker, saving and completion states. UI acknowledges each picker effect before launch, and a one-time request ID binds its callback to the original sample. Rotation retains the pending callback; process recreation never replays a write. Leaving the import session cancels work and ignores late results. Export preserves draft, preview selection and wallet state, closes streams before success and attempts partial-document cleanup on failure. This uses the installed Activity 1.8.0 `CreateDocument(mimeType)` contract and [Android SAF](https://developer.android.com/training/data-storage/shared/documents-files), without new dependencies or storage permissions.

`PrepareRecipientImport` maps headers and validates service-specific terms through `PrepareBulkBatch`, including canonical duplicates against existing rows and the unfinished editor. It preserves text identifiers, rejects Excel numeric identifiers and unsupported/formula values, and keeps decimal money exact. Explicit append rechecks selection, duplicates and capacity before returning a new draft. Invalid rows never enter payment review. Neither import nor reconnection submits payments.

`AxiaViewModel` owns the transient import session, selection and cancellable read job. The Compose picker registration is keyed by session identity; results carry that identity and are consumed only by its owner. Read results additionally require the originating navigation revision. Leaving cancels reading and discards the preview; accepted rows and the existing editor remain in the normal saved draft. Saved navigation excludes file grants, bytes, preview contents and commands, so restoration cannot reread or append twice.

Compatibility decision: Apache Commons CSV **1.14.1** handles RFC4180 records; Apache POI **5.5.1 core** is used only for the BIFF8/HSSF event reader and OLE container. Modern XLSX uses a bounded ZIP/SAX adapter available on Android, avoiding desktop OOXML rendering, XMLBeans and AWT APIs. The reader rejects DTDs, external worksheet relationships, duplicate ZIP entries and expansion over 8 MB. There is no formula evaluator or macro execution. Dependencies are pinned in the version catalog. Official references: [POI event API](https://poi.apache.org/components/spreadsheet/how-to.html#event_api), [POI release](https://poi.apache.org/download.html), [Commons CSV releases](https://commons.apache.org/proper/commons-csv/changes.html), and [Android document access](https://developer.android.com/training/data-storage/shared/documents-files). Shared synthetic fixtures exercise the same CSV/XLSX/XLS formats on the JVM and Android; platform tests cover content URIs, offline preview, selection and rotation.


Release smoke verification exposed an AGP 9.4.1 scoped-R8 package-access failure: `CollectionsKt__MutableCollectionsJVMKt` was relocated outside `kotlin.collections` while its superclass remained package-private, causing `IllegalAccessError` during AndroidX startup. `app/proguard-rules.pro` preserves only that package identity with `-keeppackagenames kotlin.collections`; optimization, shrinking and class/member renaming remain enabled. Recheck this workaround when changing AGP/Kotlin. Debug instrumentation is not a release smoke test: its test-support classes are excluded by release shrinking. Install a locally signed release APK on an explicitly selected emulator and exercise startup plus CSV/XLSX/XLS import directly, in addition to `verifyAllFlavors` and the debug device suite.


## 1,000-recipient checkpoint decision

`BulkLimits` defines a shared 1,000-recipient boundary, with one additional import header row. Import duplicate detection uses canonical identity sets in linear time, and imported row validation runs on an injected CPU dispatcher. Draft validation is reused while only editor text or display filters change. Lazy items receive prepared rows directly instead of searching the entire draft per visible item. Selection, search and confirmation remain ordinary MVI state; they never alter the full reviewed amount implicitly.

Room was evaluated for the large-list requirement. This bounded, owner-scoped demo consumes and commits whole snapshots and has no independent indexed queries; Android's supported `AtomicFile` is sufficient without adding a database dependency. `AtomicTextCheckpoint` stores UTF-8 files under app-private `noBackupFilesDir`, accessed on IO. The session snapshot commits wallet, receipts, SMS and all batch outcomes together. A mutex serializes transitions; publication follows successful atomic replacement. Once a replacement begins, a short non-cancellable commit section keeps the file and published state in agreement. Cancellation still propagates to the caller and never invents payment failure.

Navigation checkpoints serialize the latest immutable input on IO through a conflated save request; keystrokes do not encode a 1,000-row JSON payload on Main. Failed draft saving remains visible while the in-memory draft is retained. Startup restores the session and navigation before enabling actions. Missing previously committed files or decode failures show recovery instead of silently reseeding a wallet. Legacy SavedStateHandle JSON is removed only after successful migration. Submitted draft identities reconcile to their existing batch progress without executing a command. Import grants, previews, picker effects, jobs and running flags are excluded.

The checkpoints retain the existing task/session ownership, with distinct IDs for independent ViewModels and app IDs for each flavor. They are not a production ledger, cross-task account store or durable execution outbox. Removing the task can lose its checkpoint identity; retained files are not a guarantee of recovery after task dismissal. Room and lifecycle-aware cleanup/migrations should be adopted when durable account-level offline records or queryable long-term history are implemented. Accepted payment execution remains server-authoritative; no background worker or automatic resume was added.

Large demo batches advance in groups of at most 25 every simulated interval, preserving individual request IDs, attempts, results and exact refunds. Small lists keep their existing one-recipient cadence. A whole group transitions atomically, and processing rows restore for explicit resume. The history limit remains 20 batches. Demo-only sample export adds a generated 1,000-recipient CSV without changing non-demo capabilities.

Official references: [Compose performance and lazy keys](https://developer.android.com/develop/ui/compose/performance/bestpractices), [saved-state limits](https://developer.android.com/topic/libraries/architecture/saving-states), [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile), and [Room](https://developer.android.com/training/data-storage/room).


## Server wallet display

`ServerAccountAccess` coordinates successful authentication, protected credential persistence and the current-account NGN wallet read. Its result keeps a wallet lookup outcome distinct from authentication failure: transient or missing-wallet responses cannot replay credentials, create a wallet or become a demo balance. Session restoration and explicit wallet retry revalidate stored access before reading again. Results are accepted only while the captured protected session and ViewModel visit still match; cancellation remains cancellation.

`WalletRepository` and immutable exact `WalletSummary` live in domain; `HttpWalletRepository` owns the public DTO mapping. The shared `ApiHttpClient` owns the existing bounded, credential-safe OkHttp/JSON transport for authentication, wallets, purchases and public configuration. ## Electricity verification and fulfilment

The `purchases` feature shares one protected wallet/consent/recovery workflow across airtime, data and electricity.
